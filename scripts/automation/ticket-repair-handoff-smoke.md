# One-shot support repair handoff probe

The main-only `ticket-repair-handoff-smoke.yml` workflow tests the production support API's claim, claimed-detail, and repair-handoff path without starting Railway's repair bridge or calling OpenAI. It creates one short-lived `yutakasa-auto-smoke+<uuid>@example.invalid` subscriber with the existing no-payment marker, then one technical support ticket through the authenticated customer API. The app suppresses support notification email for this exact reserved address. The ticket is excluded from the normal automation queue and admin list.

Run it only after confirming production Vercel deploy SHA equals `main`, the production `support-automation-manual-review.sql` migration has been read back, Railway `TICKET_REPAIR_BRIDGE_ENABLED=false`, and GitHub variables `YUTAKASA_TICKET_REPAIR_ENABLED=false` and `YUTAKASA_AUTO_MERGE_ENABLED=false`. The workflow checks both GitHub variables again before writing. It shares the observation concurrency group with the other synthetic smoke so those workflows cannot overlap.

The probe verifies one queued repair job, one `automation_claimed` work log, one `repair_work_queued` work log, an exact list-due result, and rejection of a duplicate handoff. It never dispatches the repair workflow. In `finally`, it re-reads the exact two support messages, ticket state, work logs, job, attachment and link tables, and no-payment subscriber marker. Only then does it conditionally delete the synthetic ticket by ID, email, client request ID, status, lock, and `updated_at`; the known ticket dependents cascade. It deletes the subscriber by ID, email, and run marker and reads every synthetic table back twice. Any changed or uncertain row prevents deletion and fails the workflow for operator investigation. The workflow logs only fixed error codes and anonymous success booleans.

Success proves the deployed API and database can create an isolated repair job. It does not prove Railway scheduled dispatch, Terra investigation, draft PR creation, CI, production release observation, or ticket-specific customer resolution. These remain separate activation gates. Check the mail provider's event log after the first live run to independently confirm zero outgoing messages with the synthetic marker.
