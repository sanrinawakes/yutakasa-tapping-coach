# One-shot support repair handoff probe

The main-only `ticket-repair-handoff-smoke.yml` workflow tests the production support API's claim, claimed-detail, and repair-handoff path without starting Railway's repair bridge or calling OpenAI. It creates one short-lived `yutakasa-auto-smoke+<uuid>@example.invalid` subscriber with the existing no-payment marker, then one technical support ticket through the authenticated customer API. The app suppresses support notification email for this exact reserved address. The ticket is excluded from the normal automation queue and admin list.

Apply `ticket-repair-handoff-smoke-cleanup.sql` and read back its `service_role` EXECUTE grant and `anon`/`authenticated` denial before merging the workflow. The script also probes the cleanup RPC with invalid arguments before creating any row; a missing or inaccessible RPC stops the run. Run the workflow only after confirming production Vercel deploy SHA equals `main`, the production `support-automation-manual-review.sql` migration has been read back, Railway `TICKET_REPAIR_BRIDGE_ENABLED=false`, and GitHub variables `YUTAKASA_TICKET_REPAIR_ENABLED=false` and `YUTAKASA_AUTO_MERGE_ENABLED=false`. The workflow checks both GitHub variables again before writing. It shares the observation concurrency group with the other synthetic smoke so those workflows cannot overlap.

The probe verifies one queued repair job, one `automation_claimed` work log, one `repair_work_queued` work log, an exact list-due result, and rejection of a duplicate handoff. It never dispatches the repair workflow. In `finally`, it re-reads the exact two support messages, ticket state, work logs, job, attachment and link tables, and no-payment subscriber marker. A service-role-only database function then locks job, ticket, and subscriber in the repair claim's lock order, verifies the fixed synthetic account/content and every dependent, and deletes only an unclaimed queued job with its ticket and subscriber in one transaction. A concurrent claim or account change causes the entire cleanup to fail without deleting anything. The script reads every synthetic table back twice. Any changed or uncertain row prevents deletion and fails the workflow for operator investigation. The workflow logs only fixed error codes and anonymous success booleans.

Success proves the deployed API and database can create an isolated repair job. It does not prove Railway scheduled dispatch, Terra investigation, draft PR creation, CI, production release observation, or ticket-specific customer resolution. These remain separate activation gates. Check the mail provider's event log after the first live run to independently confirm zero outgoing messages with the synthetic marker.
