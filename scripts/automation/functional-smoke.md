# Production functional smoke for AI repair observations

`ai-repair-functional-smoke.mjs` runs only from trusted `main` in the repair observation workflow. It visits the public Production alias in desktop Chromium and mobile Chromium. Each browser uses one short-lived, HttpOnly session cookie signed with the app's production `JWT_SECRET`. The smoke sends one harmless, unique marker prompt from each browser, waits for `/api/chat` to finish streaming, checks the rendered reply, reads the exact messages from Supabase, reloads each browser, and compares the rendered reply. It checks browser exceptions and API errors. There is no OTP request, customer account, support ticket, payment-provider call, or outbound email.

## Synthetic identity and entitlement

The app uses a custom JWT cookie and `subscribers` table, not Supabase Auth users. The smoke generates a fresh reserved-domain address per run, such as `yutakasa-auto-smoke+<uuid>@example.invalid`. Before inserting, it inspects subscriber, thread, and OTP rows under that prefix. A prior subscriber is automatically removed only if its address contains a valid UUID, its marker and no-payment source match that UUID, it is older than 30 minutes, no OTP exists, and every associated thread belongs to that exact address. A newer, ambiguous, or fourth stale row blocks the run without deletion. The preflight must finish within two minutes. The generated address must also be absent. The smoke then inserts one `subscribers` row with `status='active'`, `subscription_status='active'`, null `first_payment_date`, and `myasp_data` containing an exact automation marker, `system_monitor_no_payment`, and the run UUID. The existing production access guard accepts the active subscription status without a payment date. This is a short-lived test entitlement, never a billing or MyASP record; the account has no deliverable mailbox. The smoke verifies the row's marker and fields before browsing. No production access rule is changed.

The session is signed in the trusted GitHub runner, expires after ten minutes, and reaches the browser only as an HttpOnly cookie scoped to the production alias. The Supabase service-role key remains in the runner; it is never placed in page JavaScript, a URL, a log, or a screenshot. The browser uses ordinary customer API paths and can only see its isolated account. The production database schema has `chat_threads.user_email REFERENCES subscribers(email)` and `chat_messages.thread_id REFERENCES chat_threads(id) ON DELETE CASCADE`. Repo SQL has no subscriber trigger. Before activation, inspect **live** `pg_trigger` and other sync jobs for subscriber insert/delete side effects; stop if any sends email, propagates a license, or charges.

## Runner requirements

The observation workflow needs `YUTAKASA_JWT_SECRET` set to the exact production `JWT_SECRET`, plus `YUTAKASA_SUPABASE_URL` and `YUTAKASA_SUPABASE_SERVICE_ROLE_KEY`. The monitoring `YUTAKASA_CRON_SECRET` is a separate credential and must not be assumed to match the login signing key. Install pinned `playwright` from `scripts/automation/package-lock.json` and run on the GitHub hosted `ubuntu-24.04` image with its preinstalled stable Chrome. The script selects Playwright's `chrome` channel and fails closed if the runner image lacks it; it does not download a browser every ten minutes. Configure this only after code reaches `main`; PR jobs must never receive production credentials. The observer still checks exact merged SHA and Vercel deployment ID. The smoke result is valid only for that same release and deployment.

The observer runs this browser probe only when `YUTAKASA_REPAIR_FUNCTIONAL_SMOKE_ENABLED=true` is set as a GitHub Actions variable. Keep it unset until the live subscriber trigger and external sync audit is complete, the exact production JWT secret has been registered as a GitHub Secret, and an isolated live run has passed with cleanup readback. With the variable unset, every repair observation fails the functional smoke gate and cannot mark a release verified.

## Cleanup and readback

The browser phase has a four-minute cap within the observation job's ten-minute limit. At the cap, the runner closes Chrome so its `finally` block retains time for cleanup. After closing both browser contexts, even on failure, the smoke deletes only threads whose `user_email` equals its generated reserved-domain address. It requires one returned ID for each deleted thread. The database cascade deletes messages. It then checks that no OTP row exists, deletes the marked subscriber by ID, exact email, and run UUID, and requires one returned ID. It reads back zero subscriber rows, zero thread rows, and zero messages for every created thread twice, one second apart. `testDataCleaned=true` is returned only after those checks. A leftover row or uncertain delete fails the observation; the next run reaps it only after the strict age and marker checks, and otherwise refuses to start. The UI test never touches Storage or upload paths; a browser POST to `/storage/` is treated as an error. For release evidence, separately read production `storage.objects` and report the count of objects tied to the synthetic prefix before and after the first live run.

No production test identity has been created by this code or documentation. A live synthetic run must wait for the trusted workflow, live trigger review, and required secrets. Logs should contain only error codes and counts, never the session cookie, service key, or generated AI text.
